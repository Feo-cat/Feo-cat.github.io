用 Go 写一个最小 LLM 网关：OpenAI 格式、流式转发与错误处理

发表于2026-09-03|Agent 工程
|阅读时长:17分钟
最后复核:2026-09-03|适用环境:Go 1.24.7

之前写自己的 AI 应用时，业务代码里已经出现了 base_url、API Key 和模型名这些配置，也提到过网关账本，但我还没有真正从头拆过一次：一个最小的 LLM 网关到底需要做什么？

这一轮先把范围压到最小。我只考虑 OpenAI Chat Completions 格式，只接一个上游，不做多模型路由，也不做协议转换。目标只有一个：让客户端把原本发给 OpenAI 格式接口的请求改发到本地网关，普通响应和流式响应都能正常返回。

本文示例以 Go 1.24.7 为基准，只使用标准库。它是绑定在 127.0.0.1 上的学习示例，没有调用方鉴权、限流、重试和审计，不能直接暴露到公网。

这一版到底算不算网关

请求链路很短：

客户端仍然请求 POST /v1/chat/completions，请求体仍然使用 model、messages 和 stream 等 OpenAI Chat Completions 字段。网关不理解提示词，也不修改模型输出，只负责四件事：

  1. 把上游 API Key 留在服务端。
  2. 把请求转发到固定上游。
  3. 在 stream: true 时及时转发 SSE 数据。
  4. 在网关自身失败时返回稳定错误。

这当然还不是生产级 LLM 网关，但已经有了网关最基本的边界：客户端只认识一个入口，上游地址和凭据由中间层管理。

OpenAI 当前推荐新项目优先使用 Responses API，不过 Chat Completions 仍然受支持。这里选择 /v1/chat/completions，只是为了先把最常见的 OpenAI 格式代理跑通，不在第一轮同时处理两套协议。

普通错误响应也应该透传

只要上游已经返回 HTTP 响应，无论是 200、400、401、429 还是 500，网关都保留状态码和正文。这样客户端仍然能看到上游原本的 OpenAI 格式错误。

网关只在自己无法完成请求时生成错误：

场景 状态码 错误码
请求体不是 JSON 对象 400 invalid_json
无法连接上游 502 upstream_unavailable
上游请求超过十分钟 504 upstream_timeout

这里没有加入重试。对于生成类 POST 请求，随意重试可能产生重复调用和额外费用；是否重试、哪些错误允许重试，应该等有了幂等策略后再设计。

SSE 为什么不能直接等到最后再返回

OpenAI Chat Completions 在 stream: true 时会返回 data-only Server-Sent Events。响应不是一个完整 JSON，而是一段一段到达的事件流。每个数据片段里的增量内容放在 delta 字段中。

网关不需要理解每个 delta，但必须及时把读到的字节写给客户端并调用 Flush。否则数据可能一直留在缓冲区里，客户端仍然要等到请求结束才看到内容，流式接口就失去意义。

这里使用 bufio.Reader.ReadBytes('\n') 而不是默认配置的 bufio.Scanner。Scanner 对单个 token 有默认大小限制，而流中可能出现较长的工具参数或其他数据行；逐行读取可以避免第一版额外处理这个上限。

还有一个容易忽略的边界：一旦网关已经写出 200 响应头，流中途再发生错误，就不能把状态码改成 500。示例只能结束连接并记录日志。要让客户端得到结构化的流内错误，需要进一步约定 SSE 事件协议，这一版先不做。

取消和超时是两件事

r.Context() 会在客户端断开连接时被取消。这个 Context 又被传给上游请求，因此客户端不再等待时，网关也会停止继续读取上游响应。

示例另外设置了十分钟的整请求上限，以及三十秒的 ResponseHeaderTimeout：前者限制一次生成的总时长，后者只限制发完请求后等待上游响应头的时间。没有直接给 http.Client.Timeout 填一个很短的值，因为它会覆盖读取整个响应体的过程，也就会把正常的长流一起截断。

服务端同样没有设置 WriteTimeout。普通 JSON API 通常应该设置写超时，但固定的短写超时也会限制 SSE 的总持续时间。生产环境需要结合模型最长生成时间、反向代理和负载均衡器一起设计，不能照搬普通接口的超时值。

这份最小实现故意没做什么

这篇只验证一条 OpenAI 格式链路。下面这些能力都留到后面：

  • 调用网关时的身份认证
  • 多供应商和多模型路由
  • Responses API 或其他协议转换
  • 限流、配额和费用统计
  • 重试、熔断与降级
  • 请求日志、指标和链路追踪
  • 优雅停机与更完整的安全配置

其中最先应该补的是调用方鉴权。当前服务虽然保护了上游 API Key，但它本身还没有保护，离“可以部署”仍然有明显距离。

小结

这一轮没有搭一个“万能网关”，只完成了最小闭环：客户端发送 OpenAI Chat Completions 请求，网关注入 API Key 并转给固定上游，普通 JSON 原样返回，SSE 数据逐行刷新，客户端取消也会传到上游。

对我来说，这一步最重要的不是代码量，而是先把职责边界钉住：网关可以先只是一个可靠的中转层。等真实需求出现，再往上叠路由、限流、账本和协议适配，不需要第一天就把所有能力塞进去。
