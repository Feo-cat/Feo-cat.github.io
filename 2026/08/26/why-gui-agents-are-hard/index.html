为什么 GUI agent 比 API agent 难：没有契约、状态不可见、动作不可回滚

发表于2026-08-26|系统设计
|阅读时长:5分钟

为什么最强模型碰到 GUI 任务会”逃”去调 API？

我理解下来，结构化契约之所以是 agent 可靠行动的前提，是因为它让 agent 知道该按什么格式发请求、哪些字段是什么类型；一旦出错，系统会返回校验结果或错误码，agent 至少能明白自己错了、错在哪。GUI 没有这层合同，按钮在 agent 眼里不过是一块坐标区域。界面一改版，原来的点击路径就可能悄悄失效：agent 还是点老位置，可能根本没点到目标，也可能点到了别的功能，而页面不会像 API 那样返回一个明确的错误。所以它不是“报错后失败”，而是“不报错地做错”。而这也就是标题那个问题的答案：同一件事只要有 API 可走，模型就会优先走 API——不是因为那条路更简单，是因为那条路上它做错了会有人告诉它。

状态不可见：GUI 是教科书级的部分可观测环境

拿我自己的写作助手界面来说，它的前端是 React + SSE，后端每跑完一步推一个事件过来渲染。界面上显示的东西，本质上是“后端愿意推给我的那几帧”，而不是后端真实的完整状态。昨天 debug 终审环节，页面上“终审意见”那个标题下面一片空白；只看界面，可能会以为这一步没跑，或者模型没话说。但真实状态是：模型输出了 1500 个 token，finish_reason 是 length，token 全烧在推理里，正文一个字都没写出来；而重抽的那一次还被我自己的缓存挡了回去，拿回的是同一个空响应。这些状态界面上一个都没有——它们在后端终端的日志里、在网关账本的 in/out 字段里。空白和“真的没事”，在界面上长得一模一样。

同样属于“界面误导”的还有两次。一次是页面直接跳到初稿页，看着是顺利完成了，其实是策划这一步解析出了 0 节——我这套流程里「策划」负责把选题排成若干节、「访谈」再逐节问我，0 节意味着后面整段访谈被跳过了。另一次是导师的讲解断在半句上，其实是撞了 token 上限、重抽两次、每次都被缓存挡回。而且界面还有“隐藏间隙”。我点一下发送，到下一个问题出现，中间那十几秒里到底发生了什么——重抽了几次？降级了吗？命中缓存了吗？界面只给我一个 loading，那一整段是彻底不可见的——它只告诉我“在忙”，不告诉我里面在忙什么。所以截图只能算观测：它是某一刻渲染出来的那一层，而渲染是有损的——后端没推的、推了但没渲染的、两帧之间发生完又结束的，全都不在里面。

像素会漂移，token 会燃烧：GUI 路径的双重代价

我写作用的这个 web 版应用，界面里大量按钮和可点击区域，在 GUI agent 眼里其实就是一块像素组合，位置和边界很容易受内容长度、窗口宽度、系统字体渲染这些因素影响而漂移。所以它要可靠地点中同一个按钮，只能每次交互前先截一张当前屏幕的图，重新分析定位，不能记昨天的坐标。

我这个写作助手本身就是 API 路径的例子。今天跑这篇文章跑到第三节，我的网关账本记着：23 次调用、82,674 个 token、纯模型时间 5 分半、按我写死的价目表算 3 分钱。（这是某一次运行的账本记录，不是平均值——换个选题、多问两轮，数就不一样了。）每一笔的输入输出、用了哪个模型、花了多少，都能翻出来。换成 GUI agent 来操作同一件事，它得点输入框、打字、点发送、等着、读提纲、点确认、读导师讲的、再点输入框答题……每节至少三四次交互，而每次交互之前都要先截一张图。四节下来四五十张截图，一张全屏图按一些常见视觉模型的编码可能上千 token（具体多少取决于模型、分辨率和分块策略）——光“看”这一项就已经逼近上面那 8 万的量级了，而推理和输出还一点没算。再叠上循环次数本身不确定、跑两次可能差很多，GUI 路径的总量大概率会明显高过 API 路径。

不过我觉得更要紧的不是这个倍数，是我为什么能报出上面那些数字。我能记账，是因为 API 路径有契约：一次 chat.completions 调用就是一笔，边界清清楚楚：in、out、模型名从响应里就能拿到，耗时是我的网关在调用前后打点记下来的——那是我自己的实现，不是 chat.completions 的标准字段。而 GUI 路径连“一笔”怎么算都定义不了——一次点击算一笔？还是截图加推理加动作算一笔？点错了退回来重走的那几步算不算？所以这一节和第一节其实是同一件事的两面：有契约才能记账，能记账才能预估成本。没有契约的时候，你失去的不只是可靠性，还有“你根本不知道这次要花多少钱”。

点一下就是提交：GUI 动作没有回滚原语

在网页里误点了“删除文件”，如果这个页面本身没有“撤销删除”，事后 agent 没办法像 API 那样再补一个反向操作把文件找回来。它只能完成删除，不能复原。GUI 动作没有回滚可调用，点一下就是提交，副作用已经发生。

既然不能靠“撤销那个动作”来恢复，就只能换个思路：在动作发生之前先存一个 checkpoint，或者在动作发生后立刻改自己的后续计划。我对 checkpoint 的理解是，它记这些不是为了把邮件本身撤回来，而是为了留下 agent 自己那一刻的执行状态。至少有三样：这个多步骤任务现在走到哪一步了，比如邮件已发、CRM 还没更新；这次动作的输入参数是什么，发给谁、什么标题、正文写了什么；点击之前页面和系统是什么样，草稿箱里有什么、CRM 那条记录原来长什么样。

它之所以只能叫“恢复”，不能叫“撤回”，是因为 checkpoint 改变的是 agent 的认知，不是世界的状态。邮件已经躺在对方收件箱里了，记多少东西都没用，那封信收不回来。但记了这些之后，agent 至少知道三件事：我刚才发出去的是这一封，所以能针对性地发更正信；我现在处在“已发错邮件”这个状态；后面还有“更新 CRM”没做。它能在正确的状态上决定下一步，而不是盲目往下走。

没有 checkpoint 最危险的地方还不是“补救不了”，而是“会重复犯错”。GUI 本来就看不见完整状态——点完发送，界面卡了一下没反馈，agent 根本不知道到底发出去没有，很可能再点一次，一封错邮件就变成两封。所以这一节和前面“状态不可见”那节其实是叠加的：看不见状态加上撤不回动作，合起来就是“重试会放大伤害”。checkpoint 不是时间机器，它是一份“我做过什么”的账；有了这份账，才敢让它重试。
