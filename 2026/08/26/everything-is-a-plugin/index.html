DeepSeek Harness 的「一切皆插件」：一个 agent 运行时该把扩展点留在哪里

发表于2026-08-26|更新于2026-08-26|系统设计
|浏览量:

“没有特权核心可修补”到底是什么意思

如果 Harness 把模型调用硬编码在核心里，只有工具是插件，那想替换整个模型调用的人就会卡在“核心代码不让换”这一步：模型调用不在插件边界上，想动它就得去改上游核心实现，甚至自己 fork 一份来维护。没有特权核心就是避免这个卡点——模型调用本身也做成插件，想换的时候不用碰核心源码，自己写一个对应的模型调用插件，把原来的插件替换掉就行。

Cordis 元框架：插件之间靠什么协作

我理解 Cordis 里插件之间不是靠 import 对方模块再直接调函数，而是靠 services 和 events 两类通道协作。services 解决“我需要一个能干什么的接口”，由运行时把提供方实例注入给使用方，使用方只依赖接口；events 解决“发生了一件事”，发布者发完就不管，订阅者之间互不感知。

起初我以为，如果搜索插件完成后只把结果返回给调用方而不发布事件，新加审计插件可以挂在它后面，调用方拿到结果后就触发审计。后来发现不对：旁挂插件只是让代码有机会运行，不会自动插手别的插件内部的函数调用和返回值。要拿到“搜索完成”这个信号，搜索插件必须在动作发生时主动发布事件，审计插件订阅这个事件才能收到；否则订阅再多也没用。

同理，如果 skill 插件想允许别人在执行前、执行后插入逻辑且不改代码，我起初觉得它应当主动提供接口供别人查询。实际上接口只能让别的插件主动来调用，无法在动作发生的瞬间自动触发。正确做法是发布事件，比如在 skill.execute 里通过 Cordis 上下文显式发布事件——ctx.emit("before_execute", ctx) 和 ctx.emit("after_execute", ctx)——把执行流程切出事件点；其他插件订阅这些事件来挂自己的逻辑。如果只发前后事件，执行中途没有事件点，想在“执行过程进行到一半”插入逻辑就做不到；要支持这种中途插入，被扩展方需要在中途发布一个 in_execute 事件，扩展插件通过订阅它来挂载。

services 这边，我一开始觉得两个插件都声明提供 SearchService 时，应该把两个实现都注入给调用方去挑，否则可能选不到更合适的实现。但这样调用方又会依赖具体插件，回到直接耦合。Cordis 里 service 更像“一个契约 + 一个绑定”：使用方只依赖 SearchService 接口，具体用哪个实现由 profile/装配阶段决定，运行时按装配结果注入；调用方不知道有几种实现存在。未绑定的提供者虽然声明了服务，但只是没有被激活；另一个插件也声明提供 SearchService 时，对使用方没有二义性，提供方之间才存在二义性，最终由开发者在 profile 里明确装配意图，避免同时激活多个。

把模型、工具、沙箱、Agent Loop 全部降级为插件

Standard 和 Code 预设的差别应该发生在装配层，而不是在核心里写一堆 if standard ... else if code ... 来区分；如果那样做，就违背了前面说的无特权核心原则。插件不是散在源码里的模块，而是以 npm 包形式分发，每个插件包通过声明 dsh.bundle 告诉 Harness 自己是插件，然后被 patch 进某个 profile。替换模型、换沙箱、加新技能，就变成新增或替换一个包，并在 profile 里调整挂载顺序，而不是去 fork 仓库改源码。挂载点由 profile 调整，但插件要不要跟着核心升级改，不能只看自己的 dsh.bundle 声明；如果核心升级破坏了它依赖的 services/events 接口，比如把 LLMProvider 的 Complete 改成 Generate，这个插件内部实现就编译不过，必须跟着改。反过来，如果破坏性变更只改了 profile 的装配语法，插件依赖的 services 和 events 接口本身没变，那插件就不需要改。等模型、工具、沙箱、Agent Loop 都降级成插件之后，固定不变的是那个微内核容器 cordis。所谓「可替换整个运行时」，换掉的是这些运行时能力插件——也就是激活的那一组——而不是 cordis 容器本身。换掉它们，agent 的行为逻辑完全变了，但 Harness 仍然只是在执行加载插件、卸载插件这些流程。

一个 npm 包就是一个插件：声明式装配规则

我理解下来，dsh.bundle 只是插件包里的一段自我声明，说明这个包想暴露哪些扩展能力；它本身不代表运行时一定会启用。要不要启用、按什么顺序启用，应该由 profile 的装配规则来负责，而不是把这部分决定权分给插件自己。这跟 Python 的 entry_points 有点像：包侧只是标了入口，真正加载时才会实例化。patch 也不是去改原代码，而是把插件挂到运行时的装配链上，比如给 HTTP 服务加鉴权中间件，原 handler 不用动，只把新中间件挂到合适的位置；Harness 的 patch 也是这个意思，原插件和核心都不需要改。

所以社区要接入新的模型后端时，不一定需要 fork 仓库改核心。这里要分清两种情况：如果这个后端完全兼容 OpenAI 接口，那加一个自定义 provider 配置就行：填 baseURL、api: openai-completions、以及 models 下的模型 id。密钥那一项叫 apiKeyEnv，填的是环境变量名而不是 key 本身——配置文件里从头到尾不出现密钥；但如果协议不兼容，只是改配置没法让它工作，就需要写一个新的 model adapter 插件，在包里声明 dsh.bundle，实现 Harness 期望的模型接口，再把它 patch 进 profile。换句话说，新能力靠加插件，已有能力靠改配置，两者都不需要动核心。

也有一些边界情况。比如后端完全兼容 OpenAI 接口，但需要带一个自定义请求头——而官方的 provider 配置文档里没有提到这一项。这种时候光改配置就接不上了，得写一个全新的模型适配器插件，把自定义请求头做成配置输入点暴露出来。这样同样不需要碰核心。

MCP 是扩展点的一部分，但框架只给“裸引擎”

如果 Harness 核心里直接写死一份固定 MCP server 清单，比如默认连 GitHub、文件系统、数据库三个 server，那使用者就只能用这三个服务，没法换成公司内部自建的 MCP server；除非直接 fork 核心代码，把写死的部分改掉。这就像是出厂就把插头焊死在三个插座上，想接别的插座只能把电线剪断，再把自己的线接上去。框架本身只提供一个会说 MCP 协议的插头，具体接哪个 server 应该留给插件层去决定，而不是在核心里写死。
